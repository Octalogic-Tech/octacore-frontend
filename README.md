## Start the app

Two processes: the mock API and the app.

```bash
pnpm start:api       # json-server on http://localhost:3002 (json-server/db.json)
pnpm nx serve core   # the app on http://localhost:3000
```

Set `VITE_API_URL` (see `apps/core/.env.example`) to point the app at another API.

### The FastAPI core service and sign-in

The Categories, Technologies, Clients, Projects, Countries and Users pages, and sign-in itself, are wired to the real backend, the FastAPI service in `octacore-backend`. Adding, editing and deleting a category, a technology, a client, a project or a user writes to it (Countries is read-only). A client has one primary contact (name, email and phone), kept in the service's `client_contact` table and saved by the same dialog; deleting a client deletes its contact. A technology can have one category (optional). A project has a project type (resource augmentation or product) and a billing type (retainer or fixed cost). The project's own page (click its name) lists its resources, the people on it, each with a category and an hourly rate (a resource can link to a person record, but need not), and its invoices. An invoice is made of lines (a description, a quantity and a rate), and its amount is their sum. A new invoice on a retainer project starts with one line per resource at 160 hours each, which you can change before saving; on a fixed cost project it starts with one blank line. A resource can stand for several people (its Qty), and a line is Qty x hours x rate. An invoice has a billing period; its due date fills itself to three months after the issue date and the period end to the end of the start's month. A project can have a key (like TKO) and a billing address: an invoice left without a number is numbered from the key, like OCTA/26-27/TKO/007. Each invoice can be previewed, downloaded as a PDF and emailed from the project's page; the server draws the PDF and sends the email, and needs the company, bank and mail settings described in the backend README. What a project is worth comes from its invoices: the total value is every invoice, and what is outstanding is the ones not yet marked paid. Deleting a project deletes its resources and invoices. The Invoices page, under Finance, lists every project's invoices with their client and project. It shows the ones not yet paid (overdue included) until you change the filters: status, client, project and the issue date range. Export CSV saves the rows shown. Invoices are still added, edited and marked paid on the project's own page. If the service is down, a page shows an error with a Try again button.

The Expenses page (under Finance) and the Expense types and Currencies pages (under Reference data) are wired to the same service. An expense is one charge: a name, a type, a charge date, an amount, an optional project, an optional person (from People) and notes. A recurring expense (a subscription, a tool, rent) has a frequency (monthly, quarterly or yearly), a start date and an optional end date, and the service creates one expense for every charge date from the start date on, at startup and every 24 hours, each carrying the recurring expense's person; saving one with a start date in the past creates its charges at once and says how many. A recurring expense can be paused (the charges it missed are not created when it resumes), resumed, cancelled, or deleted (its charges stay). Amounts are US dollars, kept as cents. To type an amount in another currency, add the currency on the Currencies page with its rate, how many of it make one US dollar, typed by hand: US dollars come with the migration, and rupees are yours to add with today's rate. The expense then keeps the rupee amount and the rate it was converted at, and a later change of the rate never changes it. The Expenses page has three tabs, kept in the address (`?tab=`): **Overview** (the bare address) shows one month, this month by default, with previous and next month buttons (`?month=`): its total split into one-time and recurring, the total by type, and every expense in it, one-time and generated charges together, filtered by type, project and person; **One-time** lists the expenses typed in by hand for the year, filtered by type, project, person, dates and a search, totals what it shows, and exports it as CSV; **Recurring** lists the recurring expenses with what the active ones cost each month and year. The old Recurring link still works: it opens the Recurring tab. `make seed` in the backend adds a starter set of expense types.

Every page needs a signed-in person. The service keeps the accounts; there is no sign-up, so create the first admin on the backend:

```bash
# in octacore-backend: once, then whenever you need it
make setup     # database, migrations, a JWT_SECRET in .env
ADMIN_EMAIL=you@example.com ADMIN_PASSWORD='at least ten characters' ADMIN_NAME='Your Name' make seed-admin
make run       # the API on http://localhost:5001/api/v1
```

`make seed-admin` creates the admin only if no live user has that email, and never changes an existing password. On a scratch database, put `DB_NAME=<scratch db>` in front of it (and of the `uvicorn` command that serves that database).

Keep the app and the API on the same hostname, `localhost` for both: the app on `http://localhost:3000` (the default), the API on `http://localhost:5001`. The refresh cookie only travels between same-site addresses, so mixing `localhost` and `127.0.0.1` signs you out on every reload. The API allows credentialed calls only from the origins in its `CORS_ORIGINS` setting (by default `http://localhost:4200` and `http://localhost:3000`); if the app runs anywhere else, set `CORS_ORIGINS` on the API to the app's exact origin. Point the app at another API with `VITE_CORE_API_URL` (see `apps/core/.env.example`).

To try sign-in by hand: start the API and the app as above, open `http://localhost:3000/users` and you land on the login page. Sign in with the seeded admin and you come back to the Users page. Reload: you stay signed in (the refresh cookie restores the session). Sign out from the foot of the sidebar: you are back on the login page, and signing in again lands on the overview.

`make run` serves the API on IPv4 only (`127.0.0.1`). Browsers fall back to it when `localhost` resolves to `::1` first, but Cypress's Electron does not. For a Cypress run against the real service, serve the API on `::1` instead, for example `.venv/bin/uvicorn app.main:create_app --factory --host ::1 --port 5001`, and keep `localhost` in `VITE_CORE_API_URL`. The stubbed Cypress specs intercept `http://localhost:5001` and need no service.

To check the app's expectations against the running service (opt-in, skipped otherwise), sign the checks in with the admin you seeded:

```bash
CORE_API_LIVE=1 CORE_API_URL=http://127.0.0.1:5001/api/v1 \
  CORE_API_TEST_EMAIL=you@example.com CORE_API_TEST_PASSWORD='at least ten characters' \
  pnpm exec nx test core --skip-nx-cache
```

`CORE_API_URL` names the service (default `http://localhost:5001/api/v1`). Signing in writes `last_login_date` and a refresh-token row, so even the read-only checks are not entirely read-only.

The Categories, Technologies, Clients and Users checks add records, edit them and delete them, so they run only when `CORE_API_WRITE_URL` names a service on a scratch database. Seed an admin there and start a second service on it (in `octacore-backend`):

```bash
DB_NAME=<scratch db> ADMIN_EMAIL=smoke@example.com ADMIN_PASSWORD='smoke test passphrase' ADMIN_NAME=Smoke make seed-admin
DB_NAME=<scratch db> .venv/bin/uvicorn app.main:create_app --factory --port 5002
```

then, here:

```bash
CORE_API_WRITE_URL=http://127.0.0.1:5002/api/v1 CORE_API_TEST_EMAIL=smoke@example.com \
  CORE_API_TEST_PASSWORD='smoke test passphrase' pnpm exec nx test core --skip-nx-cache
```

The live checks run in Node and carry the refresh cookie by hand, so the same-site rule above does not apply to them, and `127.0.0.1` reaches the IPv4-only service directly.

## Running tasks

To execute tasks with Nx use the following syntax:

```
nx <target> <project> <...options>
```

You can also run multiple targets:

```
nx run-many -t <target1> <target2>
```

..or add `-p` to filter specific projects

```
nx run-many -t <target1> <target2> -p <proj1> <proj2>
```

Targets can be defined in the `package.json` or `projects.json`. Learn more [in the docs](https://nx.dev/core-features/run-tasks).
